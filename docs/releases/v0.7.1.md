# Rogler Core 0.7.1 – team-map authorization sessions

Status: **source candidate**, client Xaero renderer remains a separate milestone.

## Implementation

- Introduced `TeamMapSession`: an individual viewer's authorized team-membership snapshot. It reads the current FTB party only when that party actually contains the viewer, else falls back to the viewer's own exploration; no party may be assumed from a team name or previously cached player membership.
- Tracks authorized union-chunk additions and revocations on team leave, join, or new exploration; overlapping chunks remain visible if discovered by someone still on the team. `generation` changes after membership updates to force a future client adapter to invalidate team caches.
- `ExplorationIndex.revision()` reduces unnecessary union set recomputation on unchanged membership and unchanged provenance. Version changes only when an individual player physically visits a new chunk (not when chunks are pre-generated).
- `ExplorationService` maintains in-memory sessions, reconciles them once every 40 ticks, evicts them at logout/server shutdown and never transmits coordinates/map tiles to enemy clients.
- `/rogler map session` reports an individual viewer's summary, delta and version. This is a **diagnostic**, not a Xaero renderer.
- Version stamps and offline regressions updated.

## Compatibility and no-leak requirements

- No new client packet handlers or cache write paths in v0.7.1. Xaero's fair-play server mode remains enabled from 0.7.0 and disables ordinary entity radar for all players.
- The v0.6.6 FTB party-limit fix and v0.6.5 Sable crash fix are retained.
- Personal exploration storage format unchanged (`roglerteamwars_exploration.rtwe`); original Core storage format, claim ownership and server configs not migrated.
- Server-side team session changes **cannot** remove data previously viewed, cached or screenshotted on a client. Never treat these sessions as equivalent to reversible rendered Xaero map tiles.
- DO NOT install a globally shared map addon such as Unified Xaero Worldmap for enemy teams: it merges and preserves regions among all users and does not honor revocation.

## Tests

1. Run `VERIFY.cmd` then GitHub Actions NeoForge build; source policy tests passing alone are insufficient.
2. After snapshot backup, test two FTB parties A/B and solo players on a disposable multiplayer test server.
3. A explores area U1, teammate B explores U2, both share overlap O. Call `/rogler map status` and `/rogler map session` after 2 seconds; check union U1∪U2∪O.
4. A leaves: B's `map session` shows revoked U1-only; B keeps U2 and O. Rejoin restores. B's own exploration database remains untouched.
5. B changes teams and old team retains A's own exploration only. `/rogler map session` must never contain a different party's exclusive chunks.
6. Verify loaded client maps still do NOT show shared terrain textures: expected outstanding work, not a successful Xaero test.
7. Check Xaero radar suppresses enemy icons, including old-team changes. Audit TeamPins behavior **before** enabling it: own vs other team, mutual allies, FTB public claims, and XaeroPlus.
8. Verify normal core inventory, building, claims, oversized teams, raids, Save/Restore and Sable splitting still behave like 0.7.0.

## Next: actual client Xaero adapter (0.7.2+)

- Need version-pinned Xaero API for current World Map / Minimap / XaeroPlus, explicit client cache partition between personal and transient team world-map tile pixels, encrypted/no-opposition filtering, revocation on leave and disconnect, and evidence from two real clients.
- Need a separately validated team-only position marker API; global `everyone_tracks_everyone` must stay false.
- Use TeamPins for shared team pins in the meantime; it is **not** a validated two-way sync of native local FTB/Xaero waypoints. Long-term conversion must require explicit per-pin user consent and conflict/UUID-safe tracking.
