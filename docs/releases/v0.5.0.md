# Rogler TeamWars v0.5.0 – Team UUID controls, FTB privacy audit and Core Armor

Status: **SOURCE CANDIDATE**. Local Java 21 core tests passed. NeoForge 21.1.249 compilation, FTB integration and Minecraft multiplayer runtime are **not yet verified**.

## Implemented

- **Core Armor:** `/teamwars base upgrade status` and `/teamwars base upgrade armor` beside your own placed, loaded core within 8 blocks, in Survival. Tier 0 = 10 raid HP, tier 1 = 15 raid HP (8 diamonds), tier 2 = 20 raid HP (16 diamonds + 1 netherite ingot). Validated and debited server-side, one registered team identity, no upgrade during an active raid. Upgrades are retained on placement/pack, ESCROW/recovery and **explicit** orphan adoption. No new tile/block inventory required.
- **Raid fix:** `RaidPolicy.Window` supports 20 HP without rejecting the saved raid; the chosen raid HP comes from the defender's saved armor tier when opened. Existing 10-HP raid records remain readable. Raid scoring, grace, FTB protection and attacker lock unchanged. Old player-name commands remain available.
- **Team UUID admin controls:** `/teamwars admin teams`, `/teamwars admin raidstartteam <UUID> <minutes>`, `/teamwars admin raidstopteam <UUID>`, `/teamwars admin graceteam <UUID> <minutes>`, `/teamwars admin reclaimlostteam <UUID>`, `/teamwars admin claimaudit <UUID>`. Admin commands do not require a target to be online except a raid start, which requires a defender online for fairness. Normal users never receive enemy base coordinates.
- **Orphan monitoring:** TeamWars preserves registered team UUIDs and core ledger state after FTB party deletion. Periodic reconcile logs a one-time warning for confirmed missing party IDs; no implicit takeover by the same display name and no unattended claim removal. The existing `orphanlist` and carefully gated `adoptcore` remain.
- **FTB claims:** auto-claims remain on by default for new world configs, and existing explicit configs remain unchanged. Before sync, force/verify `CLAIM_VISIBILITY=PRIVATE`; when the FTB Chunks world `ally_mode=FORCED_ALL`, refuse automatic claim creation with an error (since all viewers count as allies). Admin-only audit reports both settings. Any preexisting claims must be reviewed separately.
- **No additional third-party mods:** MC 1.21.1, NeoForge 21.1.249, FTB Teams 2101.1.11, FTB Chunks 2101.1.22, compatible FTB Library 2101.1.37, and TeamWars v0.5.0.

## Critical limitations and decisions

- FTB Teams 2101.1.11 **deletes a party when its last member leaves**. Its `PlayerLeftPartyTeamEvent` is informational (not cancellable). v0.5.0 does not rewrite FTB party internals and **cannot guarantee permanent FTB Teams party objects**. A persistent TeamWars core record is not a replacement party membership; admin reassigns confirmed orphans explicitly, and `adoptcore` still refuses when TeamWars-owned FTB claims remain until audited.
- `PRIVATE` is **not an anonymity guarantee against modified FTB Chunks clients**. FTB Chunks 2101.1.22's `SendManyChunksPacket.hidden()` replaces ownership with nil/false **but still includes the x/z chunk coordinates in network traffic**. The stock GUI normally conceals claim ownership, but a modified client could infer tracked locations. With highly secret bases, do not trust stock private claims as an anti-intelligence boundary; consider leaving FTB auto claims disabled while using the native CoreGuard, or undertake a separately tested FTB Chunks integration/packet protocol patch. No change to world `ally_mode` is performed automatically: operator decides after understanding server allies.
- Existing FTB clients may retain previously received map state until reconnect or a reset; testing one account switching teams is not a reliable privacy acceptance test. Use two truly distinct accounts/clients.
- Raids remain `raids_enabled=false` by default. Opening any raids requires OP and an online defender with no grace. Normal blocks and modded explosives stay protected. Create/AE2/FE/Chunkloading integrations are still **not implemented**. v0.5 introduces only the first usable core-upgrade tier system.
- Protection and core data are stored in the existing world SavedData. Back up **the full world including FTB data** before first launch and before downgrade. A downgrade to v0.4 will lose the persisted armor tier interpretation. Do not downgrade live without a backup restore.

1. CI compile, then `/teamwars status` prints v0.5.0. Confirm old v0.4 JAR removed.
2. `/teamwars base upgrade status` prints 10 HP, then give eight diamonds and buy tier 1; verify diamonds vanish and status reports 15 HP. Try again without enough resources; refuse without loss. Buy tier 2 for 16 diamonds + one netherite; 20 HP.
3. Save/restart; tier unchanged. Pack/re-place core; tier unchanged. Check that Creative/Spectator cannot bypass upgrade cost.
4. `/teamwars admin teams` displays stable UUID and registered mode. `/teamwars admin claimaudit <UUID>` reports private and ally_mode. Simulate `ally_mode=forced_all` **only on disposable world**; auto claims must fail safely and native CoreGuard remain active. Revert.
5. FTB team leave as last member => orphan warning and OP list. A recreated same-name party must **not** assume UUID or bearer ownership. Adopt only after old auto claims are carefully audited/cleared.
6. Run UUID raid admin commands with target offline to test graceful rejection; with defender online and grace=0, raid opens with max tier HP. After ending raid/expiry verify normal guard still denies mining, TNT and Tree Physics; points only on registered victory.
7. Two distinct clients: opponent's FTB map should not show owner/claim overlay; assess stale map and `forced_all`. Do **not** declare network metadata confidential against modified clients. Score/recovery, disconnected defender and restart persistence to be tested on real server later.
