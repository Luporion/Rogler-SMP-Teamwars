# Rogler Core 0.6.2 — bounded explosion protection and claim consistency

**Source candidate; NOT Minecraft runtime verified.** Base: `feat/v0.6.1-update` commit `48433f4` (includes GitHub watcher rename fix). Server: 1.21.1 / NeoForge 21.1.249 / Create 6.0.10. Mod ID remains **`roglerteamwars`**, and all existing `roglerteamwars_*.dat` SavedData and `roglerteamwars:*` registry IDs are preserved. JAR output stays `roglercore-0.6.2.jar`.

## What changes

1. **Explosion-local spatial protection:** `BaseGuardService.onExplosion` now snapshots the registered *PLACED* Overworld cores once per `ExplosionEvent.Detonate`, projects each configured chunk radius (0–3) to an event-local `CoreExplosionIndex`, then tests affected block coordinates using a primitive `long` hash table (no `Long` allocation per affected block). It applies the same `BaseProtectionPolicy.contains` chunk bounds as before, including negative coordinates. It does not query a world chunk or FTB per affected block. No persistent cache or delayed invalidation; placement/movement between events is immediately reflected. Only the *block list* is filtered, not entity damage.
2. **Conservative, bounded recovery:** When a core is missing from a **loaded, AIR-filled** position, observe it for 5 seconds of successive checks before attempting restoration, with at most **two automated restorations per two-minute observation window**. On a third disappearance, quarantine into existing persistent ESCROW and attempt only recorded FTB auto-claim release, rather than endlessly respawning during continuing nuclear aftereffects. Foreign-block replacement still escalates directly to ESCROW. Unloaded chunks never trigger restoration or generation, and unload resets the pending waiting period. Counts are transient and reset on process restart; world-ownership and ESCROW remain persistent.
3. **Stale claim receipt cleanup:** A recorded auto-claim whose FTB chunk is now unclaimed or owned by a different party is removed from **Rogler Core's receipt list**. No foreign FTB chunk is unclaimed. Only receipts tracked as created by Rogler Core can trigger an actual unclaim, and only if FTB still reports ownership by the original team. If the FTB team no longer exists or the FTB API is unavailable, cleanup can remain pending; use admin diagnostics. A manually unclaimed and then re-claimed chunk by the **same** party cannot be reliably distinguished by the old receipt format; do not claim perfect provenance in that scenario.
4. **Measurable handler counters:** OP `/rogler admin explosionstats` (`/teamwars` alias works) reports explosion events, affected/protected positions, average and maximum handler time in microseconds, slow-handler count (>25ms). Slow warning logged at most once per 1200 ticks. These are **ONLY Rogler Core handler timings** and cannot measure Warium's `Level.explode`, Aether loot, C2ME chunkgen, or total server MSPT.
5. **Read-only diagnostics:** `/rogler admin coreaudit` is now **read-only**, includes `loaded_missing` and `unloaded_unchecked` counts. Manual reconciliation trigger `/rogler admin corerepair apply` (OP level 4). Note: the existing server tick integrity reconciler still runs once per 20 ticks automatically; the command provides explicit on-demand retry but not an opt-out from automatic protection. A pending 5s window is not bypassed by repeated commands.
6. No additional third-party mod dependencies, new world SaveData keys, registry renaming, new chunks loaded, or general game-rule changes.

## Not included

- No guarantee against third-party direct `setBlock` or Sable sublevel transformations; those can bypass NeoForge explosion hooks. No general Warium crash fix / progressive nukes / drop-suppression implementation. v0.6.1's opt-in fusionblast Recovery remains unchanged and unverified on the original crashing world.
- No complete Warium 1.0.3/1.0.4 performance comparison or in-game timing data in this source-only build. Performance improvement must be measured with same-scene runs on separate disposable backups.
- No full transaction atomicity across FTB's independent persistence and Core SavedData; best-effort retries and explicit pending-audit status still apply.
